# Ch13 조건부 컴파일과 분할 컴파일 정리 노트

> 범위: A p2–48 (p22 구간 표지 제외) · 출처 약어: A = chap13. Conditional and Separate Compilation.pdf
> 학습 목표(Summary): 조건부 컴파일 · 구조체 패딩과 정렬 · union · 분할 컴파일 · 중복 정의 · extern과 static [A p48]

## 1. 핵심 개념

### 1-1. 조건부 컴파일
- **조건부 컴파일(conditional compilation)**: 전처리 단계에서 조건에 따라 코드 일부를 컴파일하거나 무시하는 기능. 용도는 이식성 있는 코드 작성과 디버깅 [A p2]
- 장점: 환경별 코드 관리 단순화, 모든 변형을 한 코드베이스에 유지(과용하면 가독성 저하), 불필요한 코드 제외로 컴파일 시간 감소 [A p3]

| 지시자 | 동작 [A p2] |
|---|---|
| `#if 상수식` | 상수식이 참(0이 아님)이면 블록 컴파일. `defined(NAME)`은 매크로 존재 여부 검사 |
| `#ifdef NAME` / `#ifndef NAME` | 매크로가 정의됨 / 정의되지 않음일 때 컴파일 |
| `#else` / `#elif` | 첫 조건 불만족 시 대체 블록 / else와 if 결합 |
| `#elifdef` / `#elifndef` (C23) | `#elif defined` / `#elif !defined`의 축약 |
| `#endif` | `#if`·`#ifdef`·`#ifndef` 블록 종료 |
| `#error 메시지` | 전처리 중 오류 메시지 출력 후 **컴파일 중단** [A p5] |
| `#warning 메시지` | 경고 출력, **컴파일 계속**. C23부터 표준(이전엔 GCC/Clang 확장) [A p6] |
| `#pragma ...` | 컴파일러에 추가 정보 전달 [A p7] |

- `#if` 조건의 괄호 생략 가능: `#if VER >= 3` = `#if (VER >= 3)` [A p3, p5]
- **assert와 NDEBUG** [A p4]
  - `NDEBUG` 정의 시 `assert(cond)` → `((void)0)` (아무 일도 안 함)
  - 미정의 시 조건이 거짓이면 `report(#cond, __FILE__, __LINE__, __func__)` 호출 후 중단
  - 디버그 빌드: 조건 검사, 거짓이면 중단 / 릴리스 빌드: `-DNDEBUG`로 컴파일 → 모든 assert 제거
- **#pragma** [A p7, p8]
  - 지시자 자체는 C/C++ 표준, 각 pragma의 동작은 구현 정의, 모르는 pragma는 무시
  - 표준 pragma(C)는 부동소수점 동작 제어: C99 `FP_CONTRACT`, `FENV_ACCESS`, `CX_LIMITED_RANGE` / C23 추가 `FENV_ROUND`, `FENV_DEC_ROUND` (예: `#pragma STDC FENV_ACCESS ON`)
  - 대부분은 컴파일러 확장. MSVC 예: `#pragma warning(disable : 4446)`(경고 C4446 끄기), `#pragma optimize("", off)` / `("", on)`(구간 최적화 끄기·켜기)

### 1-2. 구조체 패딩과 정렬
- **바이트 정렬(byte alignment)**: 멤버에 효율적으로 접근하도록 메모리에 배치하는 방식. 컴파일러가 멤버 사이에 **패딩(padding)** 바이트 추가 → 접근 속도↑, 메모리 사용↑ [A p12]
- 기본 동작: 멤버를 자연 경계(4 또는 8바이트)에 맞춰 패딩. 패딩·정렬은 C 표준에서 **구현 정의**, 실제 배치는 아키텍처·컴파일러 설정에 따라 다름 [A p10, p13]
- **`#pragma pack(push, 1)`**: 패킹 정렬 1바이트(패딩 없음) / **`#pragma pack(pop)`**: 이전 정렬 복원. 표준 아님, MSVC·GCC·Clang이 확장으로 지원 [A p9, p10]
- **packed 구조체가 느린 이유**: CPU는 정렬된 덩어리(4/8바이트) 단위로 읽음 → 경계에 걸친 멤버(offset 1의 `int b`)는 두 번 읽음. 일부 CPU는 비정렬 접근 시 fault → 필요할 때만 사용 [A p10, p11]
- **`offsetof(type, member)`** (`<stddef.h>`): 멤버의 바이트 위치. `size_t` 값은 `%zu`로 출력 [A p15]
- **`_Static_assert(조건, "메시지")`**: 컴파일 시점 검사, 거짓이면 빌드 실패, 두 번째 인자는 실패 시 메시지 [A p15]

### 1-3. union
- **공용체(union)**: 구조체와 비슷하나 모든 멤버가 **같은 시작 주소의 같은 메모리** 공유 [A p16, p17]
- 한 번에 한 멤버만 유효: 마지막에 쓴 멤버만 의미 있는 값, 하나를 쓰면 나머지를 덮어씀
- **타입 퍼닝(type punning)**: 한 멤버로 쓰고 다른 멤버로 읽기 → 같은 바이트를 다른 타입으로 재해석 [A p16]
- 용도: 메모리 제약 환경(버퍼 하나를 여러 타입이 공유해 RAM 절약), 타입 퍼닝(float 비트를 int로 읽기), 하드웨어 레지스터 매핑(전체 워드 또는 비트필드로 접근) [A p17]

### 1-4. 미리 정의된 매크로 [A p20, p21]
| 매크로 | 의미 | 예시 값 |
|---|---|---|
| `__FILE__` | 현재 소스 파일 이름 | `"example.c"` |
| `__LINE__` | 현재 줄 번호 | `15` |
| `__DATE__` / `__TIME__` | 컴파일 날짜 / 시각 | `"Mar 10 2023"` / `"14:55:02"` |
| `__STDC__` | ANSI C 표준 준수 여부 | `1` |
| `__STDC_VERSION__` | 준수하는 C 표준 버전 | `199901L` (C99) |
| `__cplusplus` | C++ 코드에서만 정의, C++ 표준 버전 | `201103L` (C++11) |
- `__func__`: 현재 함수 이름 [A p20]

### 1-5. 분할 컴파일
- **빌드 흐름** [A p23]: 소스 `.c` → 전처리기(`#include`, `#define`, `#if`; `.i`) → 컴파일러(파일 하나씩; `.o`) → 링커(파일 간 심볼 연결, 이름 해결) → 실행 프로그램
- **분할 컴파일을 쓰는 이유**: `.c` 하나를 바꾸면 그 파일만 재컴파일, 링커가 나머지 `.o` 재사용 [A p23]

| 구분 | 선언(declaration) | 정의(definition) [A p24] |
|---|---|---|
| 의미 | 이름이 있다고 알림 | 실체(메모리나 본문) 생성 |
| 함수 | `void printDocument(Document d);` | `void printDocument(Document d) { ... }` |
| 전역 변수 | `extern Config globalConfig;` | `Config globalConfig = { 50, ENGLISH };` |
| 규칙 | 모든 파일에서 반복 가능 | 프로그램 전체에서 **정확히 한 번** |
| 위치 | `.h` (선언·타입·매크로, 포함하는 모든 파일이 공유) | `.c` (한 번 컴파일되어 자기 `.o`로) |

- 타입 정의(`struct`, `typedef`)는 메모리를 만들지 않음 → 헤더에 둠(include guard로 보호) [A p24]
- 모듈 구성 예: `document.h`(공유 타입) + 모듈별 헤더(`document_editor.h` 등, 각각 `document.h` 포함) + 모듈별 `.c` [A p25]
- **기능 플래그**: `#if defined(FEATURE_X)`로 함수 정의와 그 호출을 함께 감쌈 → 플래그 없는 빌드는 호출도 생략 [A p26–p28]
- `-DNAME`: 컴파일 시 매크로 NAME 정의 → `#if defined(NAME)` 코드 활성화 [A p31]

### 1-6. Makefile과 make
- **Makefile**: 유닉스 계열 환경의 빌드 과정 관리 파일. 실행할 작업 집합을 정의해 컴파일·링크 단순화 [A p31]
- 주요 변수: `CC`(컴파일러), `CFLAGS`(`-Wall -g -D...`), `INCLUDES`(헤더 경로), `LFLAGS`(라이브러리 경로), `LIBS`(링크할 라이브러리), `SRCS`(소스 목록), `OBJS=$(SRCS:.c=.o)`(각 이름의 .c를 .o로 치환), `MAIN`(실행 파일 이름) [A p31]
- 규칙 형식: `target: dependencies` 다음 줄에 `command` [A p33]
- 자동 변수: `$<` = .c 파일, `$@` = .o 파일(타깃) [A p32] / `$^` = 의존 파일 전체(보충) [A p33]
- 핵심 규칙 [A p32]: `all: $(MAIN)`, `$(MAIN): $(OBJS)`(링크 단계), `.c.o:`(접미사 규칙, 각 .c → .o), `clean:`(`$(RM) *.o *~ $(MAIN)`), `depend:`(`makedepend $(INCLUDES) $^`), `.PHONY: depend clean`
- 명령: `make`(전체 빌드), `make clean`(.o 삭제), `make depend`(.h 의존성 추가) [A p32]
- **재빌드 규칙**: 의존 파일이 타깃보다 **새로울 때만**(파일 타임스탬프) 타깃 재빌드 → 바뀐 파일만 재컴파일, 변경 없으면 `'...' is up to date.` [A p33]

### 1-7. 중복 정의와 include guard
- 헤더가 여러 번, 서로 포함되므로 같은 정의가 여러 번 나타나기 쉬움 [A p34]
- 여러 `.c`에서 반복 가능한 것은 **타입 정의뿐**: 모양만 설명(메모리·링커 심볼 없음), 각 `.c`가 따로 컴파일되므로 사용하는 파일마다 정의 필요 → 공유 헤더. 링커는 함수·전역 변수만 연결. 모든 파일에서 동일해야 하며 공유 헤더가 이를 보장(C++ ODR도 타입에 같은 규칙) [A p34]

| 중복 상황 | 허용? | 방지법 [A p34] |
|---|---|---|
| 한 `.c` 안에서 같은 타입 두 번 정의 | 불가: 컴파일 오류 | include guard |
| 여러 `.c`에 같은 `typedef` | 허용 | 불필요 |
| 여러 `.c`에 같은 함수 정의 | 불가: 링크 오류 | 한 번만 정의, 헤더에 프로토타입 |

- **ODR(One Definition Rule, 단일 정의 규칙)**: 함수·전역 변수는 프로그램 전체에서 한 번만 정의. 두 번째 정의 → `multiple definition` 링크 오류. 선언(프로토타입, `extern`)은 반복 가능 [A p35]
- **include guard**: `#ifndef X_H` / `#define X_H` / 내용 / `#endif`. 같은 헤더가 한 번역 단위에 여러 번 들어와도 첫 사본만 남김 [A p37, p38]
- **`#pragma once`**: 한 줄짜리 가드 [A p39]

| | include guard | `#pragma once` [A p39] |
|---|---|---|
| 표준 | 표준 C, 모든 컴파일러 | 비표준, GCC·Clang·MSVC 지원 |
| 단점/장점 | 헤더마다 고유 매크로 이름 필요(같은 이름이면 조용히 서로 가림) | 한 줄, 이름 충돌 없음 |
| 선택 | 이식성이 중요하면 가드 | |

### 1-8. extern, static, 연결
- **`extern`**: "여기서 선언, 정의는 어딘가(다른 파일 또는 같은 파일)". 파일 간 변수·함수 공유 [A p40]
- **`static`**: 한 파일 안에 캡슐화 [A p40]
- **연결(linkage)**: 링커가 이름을 파일 간에 연결할 수 있는지 [A p41]

| 연결 | 보이는 범위 | 대상 [A p41] |
|---|---|---|
| 외부(external) | 모든 파일 | 전역 변수·함수의 기본값 |
| 내부(internal) | 자기 파일만 | 파일 범위 `static` |
| 없음(none) | — | 지역 변수, 매개변수 |

- **static의 두 의미** [A p41]: 파일 범위 = 다른 파일에서 이름 숨김(가시성) / 함수 안 = 호출 사이 값 유지(수명)
- 공유 전역 패턴 [A p42]: 헤더에 `extern` 선언, `.c` 하나에서 정의, 사용하는 파일은 헤더만 포함 → 링커가 연결. 정의하는 `.c`도 그 헤더를 포함해 컴파일러가 선언·정의 일치 검사

## 2. 핵심 사실(수치)
- `{char a; int b;}`: 기본 8바이트(a, 패딩 3, b는 offset 4) / `pack(1)` 5바이트(b는 offset 1, 4바이트 경계 걸침) [A p9–p11]
- **정렬 규칙(x86-64)** [A p13]: 각 멤버는 자기 정렬의 배수 위치에서 시작(`short` 2, `int` 4, `double` 8) / 구조체 크기는 가장 큰 멤버 정렬의 배수 → 꼬리 패딩(tail padding) / C는 선언 순서 유지, 컴파일러는 멤버 재배치 안 함
- `struct student {char ch1; short num; char ch2; int score; double grade; char ch3;}`: offset ch1 0, num 2, ch2 4, score 8, grade 16, ch3 24 → **32바이트**(패딩 15) [A p13, p15]
- 큰 멤버부터(`grade, score, num, ch1, ch2, ch3`) → **24바이트**(패딩 7) [A p14]
- **union 크기** = 가장 큰 멤버 크기를 정렬 배수로 올림. 예: `union { char c[5]; int i; }` = 8바이트 [A p17]
- `data.f = 220.5;` 후 `data.i` 출력 → `1130135552` (220.5 아님) [A p16]

## 3. 원리·결론
- `#error`는 멈추고 `#warning`은 계속 진행 [A p5, p6]
- 정렬 = 속도와 메모리의 교환. packed는 메모리 절약, 대신 느려지거나 fault 가능 [A p10, p12]
- 같은 멤버라도 선언 순서에 따라 패딩량이 달라짐 [A p14]
- 비트필드: 선언 순서는 유지되나 첫 필드가 하위·상위 비트 중 어디인지는 구현 정의 → 레지스터 매핑 출력값은 컴파일러마다 다름(이식성 없음) [A p19]
- 컴파일 오류는 **한 파일 안**(문법, 선언 안 된 이름, 타입 두 번 정의), 링크 오류는 **파일 사이**(함수·전역 두 번 정의, 정의 없음 = `undefined reference`) [A p23]
- 링커는 함수를 **이름만으로** 매칭 → 본문이 달라도 같은 이름이면 충돌. 해결: 이름 변경 또는 `static` [A p34]
- 반복 `typedef`만은 허용(C11), 반복 `struct` 본문은 불가 [A p38]

## 4. 문제 유형별 접근
- 구조체 크기 계산: 멤버별 정렬 확인 → 앞에서부터 정렬 배수 위치에 배치(빈칸 = 패딩) → 끝을 최대 정렬 배수로 올림
- 패딩 줄이기: 정렬이 큰 멤버부터 선언
- 레이아웃 확인: `offsetof`로 위치 측정, `_Static_assert`로 크기 고정 검사(추측 금지) [A p15]
- union 크기: 최대 멤버 크기 → 최대 정렬 배수로 올림
- 기능 켜고 끄기: 코드에 `#if defined(FEATURE_X)` → `gcc -DFEATURE_X` 또는 `CFLAGS`에 추가
- 수동 분할 빌드: `gcc [-D...] -c x.c -o x.o`(파일마다) → `gcc a.o b.o ... -o prog`(링크) [A p30]
- 링커 오류 해석 [A p36]
  - `multiple definition`: 같은 함수·전역이 두 `.c`(또는 둘이 포함한 헤더)에 정의 → 정의 하나만 남기고 헤더엔 프로토타입·`extern`만
  - `undefined reference`: 선언만 있고 정의 없음, 또는 해당 `.c`/`.o`를 빌드에서 빠뜨림 → 정의 추가 또는 gcc 명령·Makefile에 파일 추가
- 전역 공유: 헤더에 `extern` 선언 + `.c` 하나에 정의 / 파일 전용: `static`

## 5. 실수 포인트
- `assert` 안에 꼭 필요한 작업 금지: `assert(init() == 0)`은 릴리스에서 `init()` 호출 자체가 사라짐 [A p4]
- `#pragma pack`, `#pragma once`는 표준 아님 [A p9, p39]
- 헤더에 함수 본문·전역 정의를 넣으면 포함한 `.c`마다 정의 생김 → `multiple definition` [A p36]
- Makefile 의존성에 `.h`도 적어야 헤더 변경 시 재빌드됨(`make depend`가 자동 추가) [A p33]
