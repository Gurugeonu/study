## 이야기의 시작: 토리의 일기장 프로그램

토리가 C로 일기장 프로그램을 만들었어요. 오늘 일기를 입력하고 프로그램을 껐다가 다시 켰더니, 일기가 몽땅 사라졌어요. 변수는 프로그램이 끝나면 함께 사라지기 때문이에요.

이 단원 내내 쓸 그림 하나를 정해 둘게요.
- **창고**: 디스크. 공책(파일)이 보관된 곳이에요.
- **창고지기**: 운영체제 커널. 창고에는 창고지기만 들어갈 수 있어요.
- **책상 위 바구니**: 버퍼. 토리가 공책 내용을 조금씩 옮겨 두는 곳이에요.

Part 1에서는 바구니를 알아서 관리해 주는 도우미(C 표준 입출력, stdio)를 쓰고, Part 2에서는 창고지기에게 직접 부탁하는 방법(시스템 호출)을 배워요.

# Part 1. C 표준 입출력

## 1. 왜 파일인가, 그리고 "모든 것은 파일"

파일은 두 가지 문제를 풀어 줘요 [A p4].
- **지속성(persistence)**: 프로그램이 끝나도 데이터가 남아요. 토리의 일기가 살아남는 이유예요.
- **공유(sharing)**: 다른 프로그램이나 다음 실행에 데이터를 넘길 수 있어요.

Unix에는 "모든 것이 파일"이라는 말이 있어요. 디스크뿐 아니라 터미널과 장치도 똑같은 파일 인터페이스로 읽고 써요. 창고지기 입장에서는 공책이든 키보드든 "바이트를 주고받는 창구"일 뿐이에요.

C에서는 파일을 `FILE *`라는 포인터로 다루고, 흐름은 항상 같아요.

```c
fopen → 읽기/쓰기 → fclose
```

키보드 입력(stdin), 화면 출력(stdout), 오류 출력(stderr)은 프로그램이 시작할 때 이미 열려 있어요.

그런데 공책에 무엇을 어떤 모양으로 적어야 할까요?

## 2. 텍스트 파일과 바이너리 파일

공책은 두 종류예요 [A p5].

**텍스트 파일(text file)** 은 ASCII나 UTF-8로 쓴 글자들이 개행 문자로 줄을 이루는 파일이에요. 메모장으로 열면 사람이 바로 읽을 수 있고, 인코딩이 표준이라 어느 컴퓨터로 옮겨도 잘 읽혀요(이식성이 높아요). 문서, 소스코드, 설정 파일이 여기에 속해요.

**바이너리 파일(binary file)** 은 데이터를 이진 형식 그대로 담아요. 구조는 응용 프로그램마다 다르고 표준 줄 끝도 없어서, 해석할 수 있는 전용 프로그램이 있어야 읽을 수 있어요. 시스템에 따라 달라질 수도 있어요. 실행 파일, 이미지, 오디오·비디오, 데이터베이스가 예예요.

`xxd`로 바이트를 직접 들여다보면 차이가 보여요.
- `hello.txt`(Hello, World 두 줄): `48 65 6c 6c 6f 0a 57 6f …`. 모든 바이트가 출력 가능한 글자이거나 `0a`(`'\n'`)예요. Windows에서는 줄바꿈이 `0d 0a`(`'\r\n'`) 두 바이트로 저장돼요.
- `image.png`: `89 50 4e 47 0d 0a 1a 0a`로 시작하는 시그니처, 이어서 `IHDR` 헤더 청크, 그 안에 `00 00 01 e0`(480), `00 00 01 40`(320)이라는 가로·세로 크기가 들어 있어요. 글자로 읽으면 의미가 없는 바이트들이에요.

공책 종류를 알았으니 이제 창고에서 공책을 꺼내 봐요.

## 3. 파일 열고 닫기: fopen, fclose, perror

**왜 필요한가.** 공책을 쓰려면 먼저 "이 공책을 이런 용도로 쓰겠다"고 알려야 해요.

**정의.** [A p6]
```c
FILE *fopen(const char *name, const char *mode);
fp = fopen("a.txt", "r");   // "r" 읽기, "w" 쓰기, "a" 덧붙이기
fclose(fp);
```
`fopen`은 파일 포인터(file pointer), 즉 `FILE` 구조체를 가리키는 포인터를 돌려줘요.

**실패 처리.** 파일이 없거나 권한이 없으면 `fopen`은 `NULL`을 돌려줘요. 이때 `perror`를 부르면 실패 이유가 stderr에 찍혀요 [A p7].
```c
if (fp == NULL) { perror("a.txt"); return 1; }
```
- 파일이 없으면 `a.txt: No such file or directory`
- 읽을 권한이 없으면 `a.txt: Permission denied`

**어디서 찾나.** `fopen("a.txt", …)`처럼 이름만 주면 **현재 작업 디렉터리**에서 찾아요 [A p8]. 현재 작업 디렉터리는 프로그램을 *실행한* 디렉터리예요. 실행 파일이 놓인 폴더와 다를 수 있어서, "분명 파일이 옆에 있는데 못 찾는" 일이 생겨요. 다른 위치라면 경로를 적어요. Windows 경로는 `"C:\\source\\another_example.txt"`처럼 `\`를 두 번 쓰거나, `"C:/source/another_example.txt"`처럼 `/`를 써요.

> 보충: `\`를 두 번 쓰는 이유는 C 문자열 안에서 `\`가 이스케이프 문자이기 때문이에요.

그런데 공책을 열 때 "읽기만"인지 "새로 쓰기"인지에 따라 무슨 일이 달라질까요?

## 4. 열기 모드

모드는 "공책이 이미 있을 때"와 "없을 때" 무엇을 하는지를 정해요 [A p9].
- `"r"`: 읽기 전용. 없으면 오류.
- `"w"`: 쓰기 전용. 있으면 내용을 **덮어쓰고**, 없으면 만들어요.
- `"a"`: 끝에 덧붙여 쓰기. 있으면 덧붙이고, 없으면 만들어요.
- `"r+"`: 읽기 중심인데 쓰기도 돼요. 있으면 자르지 않고 열고, 없으면 오류.
- `"w+"`: 쓰기 중심인데 읽기도 돼요. 동작은 `"w"`와 같아요.
- `"a+"`: 읽기·쓰기 둘 다, 쓰기는 덧붙이기. 없으면 만들어요.
- `"wx"`, `"w+x"`: 배타적 생성(C11). 파일이 이미 있으면 **실패**하고, 없을 때만 만들어요. 남의 파일을 실수로 덮어쓰지 않게 해 줘요.
- `"rb"`, `"wb"`, `"ab"` 등: 위와 같되 바이너리 모드예요.

`r+`와 `w+`는 헷갈리기 쉬워요 [A p10]. `r+`는 기존 내용을 **보존**하고, 위치 표시자가 가리키는 곳 어디서든 읽고 써요. 있는 일기를 고칠 때 써요. `w+`는 여는 **순간** 내용을 지워서 새 빈 공책처럼 만들어요. 옛 내용을 버리고(또는 새로 만들어) 읽기·쓰기를 둘 다 할 때 써요.

갱신 모드(`r+`, `w+`, `a+`)에서 읽기와 쓰기를 오갈 때는 규칙이 있어요. 이건 바구니를 이해해야 풀리니 13절에서 다룰게요.

그럼 `fopen`이 돌려준 그 "포인터"는 정확히 무엇을 가리킬까요?

## 5. 스트림, FILE 구조체, 버퍼

**스트림(stream)** 은 바이트가 줄지어 흐르는 것을 추상화한 개념이에요 [A p11]. 읽기·쓰기 모두에 쓰이고, 상대가 파일이든 장치·파이프·소켓·메모리 버퍼든 똑같은 방법으로 다룰 수 있게 해 줘요. 그래서 프로그램이 장치나 운영체제에 덜 묶여요. C에서는 이것들을 모두 **파일 스트림(file stream)** 으로 관리하고, `FILE *`로 붙잡아요. stdin, stdout, stderr는 콘솔용으로 미리 정의된 표준 스트림이에요.

`fopen`은 세 가지 일을 해요 [A p12].
1. 파일을 열어요.
2. 메모리에 파일 스트림, 즉 **책상 위 바구니**를 만들고 창고의 실제 파일과 연결해요.
3. 그 바구니에 닿는 손잡이, 파일 포인터를 돌려줘요. 이후 모든 입출력은 이 손잡이로 해요.

같은 `FILE *`가 장치(`fopen("/dev/urandom", "rb")`로 난수 바이트 읽기, `/dev/tty`에 `fprintf`), 파이프(`popen`), 소켓(`fdopen`), 메모리(`fmemopen`)에도 쓰여요. "모든 것이 파일"이 C 코드에서 이렇게 드러나요.

**FILE 구조체** 안에는 파일 디스크립터(운영체제가 열린 파일을 구별하는 정수), 버퍼, 오류 표시자, 현재 위치 표시자 등이 들어 있어요 [A p13]. 정확한 구성은 C 표준이 정하지 않아서 직접 건드리지 않고 `fopen`, `fclose`, `fread`, `fwrite`, `fprintf`, `fscanf`, `getc`, `putc`, `fgets`, `fputs` 같은 함수로만 다뤄요.

**버퍼가 왜 중요한가.** 창고지기를 부르는 일(시스템 호출)은 비싸요. 바구니가 없으면 `getc`로 한 글자 읽을 때마다 창고지기를 불러야 해서 프로그램이 크게 느려져요. 바구니에 한꺼번에 받아 두고 한 글자씩 꺼내면 창고지기를 훨씬 덜 불러요.

손잡이가 생겼으니, 이제 한 글자씩 옮겨 볼까요?

## 6. 문자 입출력과 EOF

**함수들.** [A p14]
```c
c = getc(fp);    // 매크로일 수 있음
c = fgetc(fp);   // 함수
int ungetc(int c, FILE *fp);  // c를 스트림에 되돌려 놓기
putc(c, fp);  fputc(c, fp);   // 한 글자 쓰기
feof(fp);  ferror(fp);        // EOF면 / 오류면 0이 아닌 값
```
`getc`/`putc`는 매크로로 구현될 수 있고, `fgetc`/`fputc`는 진짜 함수예요. `ungetc`는 방금 읽은 글자를 바구니에 다시 넣어서 다음 읽기에서 또 나오게 해요.

**EOF.** 파일 끝이나 오류가 나면 `getc`는 `EOF`를 돌려줘요 [A p15]. `EOF`는 기호 상수(매크로)이고, C 표준은 "음의 정수"라는 것만 요구해요. 보통 `stdio.h`에 `#define EOF (-1)`로 정의돼 있어요. 숫자 대신 이름을 쓰는 이유는 프로그램이 구체적인 값에 기대지 않게 하려는 거예요.

그래서 읽은 글자는 `char`가 아니라 **`int`** 에 담아야 해요(EOF가 음의 정수라서).

> 보충: 한 바이트가 가질 수 있는 256가지 값과 EOF를 모두 구별하려면 `char`보다 넓은 자리가 필요해요.

**예제: 파일 복사** [A p16]. 핵심은 한 줄이에요.
```c
while ((c = getc(fp1)) != EOF)
    putc(c, fp2);
```
오류를 꼼꼼히 다루는 판은 단계가 늘어나요.
1. `argc != 3`이면 사용법을 stderr에 알리고 끝내요.
2. 원본을 `"r"`로 열고, 실패하면 `perror` 후 종료해요.
3. 대상을 `"w"`로 열고, 실패하면 **이미 연 원본을 닫고** 종료해요.
4. 복사 루프가 EOF로 끝나면 `ferror(fp1)`로 "진짜 끝"인지 "읽기 오류"인지 확인해요.
5. `fclose(fp2) == EOF`인지 봐요. 쓴 데이터는 바구니에 남아 있다가 `fclose`가 비울 때 창고로 가기 때문에, 쓰기 오류는 이 순간에야 드러날 수 있어요. 닫기 전에 `ferror(fp2)`도 받아 둬요.

글자 하나씩 말고, "이름 숫자"처럼 형식이 정해진 내용은 어떻게 읽을까요?

## 7. 서식 입출력

`scanf`/`printf`에 파일 포인터를 붙인 판이에요 [A p17].
```c
int fscanf(FILE *fp, const char *format, ...);
int fprintf(FILE *fp, const char *format, ...);
```
예제는 `"단어 숫자"` 줄들을 읽어 단어를 대문자로, 숫자를 두 배로 바꿔 써요.
```c
while (fscanf(inputFile, "%99s %d", str, &num) == 2) { … fprintf(outputFile, "%s %d\n", str, num * 2); }
```
반복 조건 `== 2`는 "두 개 다 읽었을 때만" 반복한다는 뜻이에요.

> 보충: `fscanf`는 성공적으로 채운 항목 수를 돌려줘요. 그래서 `== 2`로 검사할 수 있어요.

`%99s`는 `char str[100]`에 `'\0'` 자리를 남기고 최대 99자만 읽게 해요. 대문자 변환은 `toupper((unsigned char) str[i])`처럼 `unsigned char`로 바꿔서 넘겨요.

그런데 `printf`는 파일 포인터 없이 화면에 쓰잖아요. 그건 어떤 공책일까요?

## 8. 표준 스트림 세 개

프로그램이 시작하면 C 런타임이 공책 세 권을 미리 열어 둬요 [A p18]. 이것들은 `stdio.h`에 정의된 `FILE *`형 매크로예요.
- `stdin`: 표준 입력, 보통 키보드 (fd 0)
- `stdout`: 표준 출력, 보통 화면 (fd 1)
- `stderr`: 표준 오류, 보통 화면 (fd 2)

정상 종료 때는 런타임이 이것들을 비우고 닫아요. `getchar`, `putchar`도 사실 매크로예요.
```c
#define getchar()  getc(stdin)
#define putchar(c) putc((c), stdout)
```

`getchar`/`putchar` 에코 예제는 `ch == EOF`가 될 때까지 읽은 글자를 그대로 출력해요 [A p19]. 키보드로 EOF를 보내려면 Windows에서는 줄 처음에 `Ctrl+Z`를 누르고 Enter, Unix/Linux에서는 줄 처음에 `Ctrl+D`를 눌러요. `Ctrl+D`는 글자가 아니에요. 터미널이 입력을 끝내고, 그래서 `getchar`가 EOF를 돌려줘요.

**바구니 유무** [A p20]. stdin과 stdout에는 바구니가 있어요. stderr에는 **바구니가 없어요**.

> 보충: 그래서 오류 메시지는 쌓이지 않고 곧바로 화면에 나타나요.

출력이 두 갈래(stdout, stderr)로 나뉘어 있으면 무엇이 좋을까요?

## 9. 리다이렉션

셸에서 `n>`은 "fd n번 출력을 파일로 돌려라"는 뜻이고, 그냥 `>`는 `1>`의 줄임이에요 [A p21].
- `./a.out > out.txt`: stdout은 out.txt, stderr는 화면
- `./a.out 2> err.txt`: stdout은 화면, stderr는 err.txt
- `./a.out > out.txt 2> err.txt`: 각각 따로
- `./a.out > all.txt 2>&1`: 둘 다 all.txt
- `./a.out 2> /dev/null`: 오류는 버려요
- `./a.out 2>> err.txt`: 오류를 err.txt 끝에 덧붙여요

**주의 1: 순서.** `2>&1`은 "fd 2를 *그 순간* fd 1이 가리키는 곳으로"라는 뜻이에요. `> all.txt 2>&1`은 fd 1을 먼저 파일로 돌린 뒤 fd 2를 따라 보내니 둘 다 파일로 가요. `2>&1 > all.txt`는 fd 2가 아직 화면인 fd 1을 따라간 다음 fd 1만 파일로 바뀌니, stderr는 여전히 화면에 나와요.

**주의 2: 띄어쓰기.** `2 > err.txt`라고 쓰면 `2`가 프로그램 인자가 되고 stdout이 리다이렉트돼요. `2>`는 붙여 써요.

이렇게 결과와 오류를 갈라 둘 수 있으니, 오류는 반드시 stderr로 보내야겠죠?

## 10. 오류 처리와 exit

**예제: cat 같은 프로그램** [A p22]. 파일 이름들을 받아 차례로 stdout에 이어 붙이고, 인자가 없으면 stdin을 stdout으로 복사해요.
```c
if (argc == 1) filecopy(stdin, stdout);
… if ((fp = fopen(*++argv, "r")) == NULL) { fprintf(stderr, "%s: can't open %s\n", prog, *argv); exit(1); }
if (ferror(stdout)) { fprintf(stderr, "%s: error writing stdout\n", prog); exit(2); }
```
`filecopy`는 `fgetc`/`fputc` 루프예요. 오류 메시지를 stderr로 보내기 때문에 결과를 파일로 리다이렉트해도 메시지는 화면에 보여요. 마지막 `ferror(stdout)`은 지금까지 stdout 쓰기에서 디스크가 꽉 차거나 파이프가 끊기는 등의 오류가 있었는지 확인해요. 열기 실패는 `exit(1)`, 쓰기 오류는 `exit(2)`로 끝내요.

**exit.** [A p23]
```c
void exit(int status);
```
프로그램을 끝내고 운영체제에 제어를 돌려줘요. 끝내기 전에 열린 출력 파일마다 `fclose`를 불러 바구니를 **플러시(flush)** 해요. 플러시는 바구니에 대기 중인 데이터를 실제 목적지로 보내는 일이에요. 즉 모든 출력 스트림이 비워지고 모든 스트림이 닫혀요.
- 종료하지 않고 비우려면 `fflush(fp)`를 불러요. 이때 데이터는 창고지기의 임시 선반(커널 **페이지 캐시**)까지 가고, 아직 창고(디스크)에 들어간 건 아니에요. 이 이야기는 Part 2의 fsync에서 이어져요.
- 종료 상태: `0` 또는 `EXIT_SUCCESS`는 정상 종료, 0이 아닌 값 또는 `EXIT_FAILURE`는 비정상 종료나 오류예요.

토리는 일기를 한 글자씩이 아니라 한 줄씩 읽고 싶어졌어요.

## 11. 줄 입출력

### fgets와 그 구현

```c
char *fgets(char *s, int n, FILE *iop);
```
최대 n−1자까지 읽어요. 개행을 만나면 그 개행까지 `s`에 **넣고** 멈추고, EOF에서도 멈춰요. 끝에는 항상 `'\0'`을 붙여요. 읽기 오류가 났거나 아무것도 못 읽고 EOF를 만났으면 `NULL`, 아니면 `s`를 돌려줘요 [A p24–25].

K&R 구현을 한 줄씩 따라가면 이 규칙이 왜 생기는지 보여요 [A p24].
```c
while (--n > 0 && (c = getc(iop)) != EOF)
    if ((*cs++ = c) == '\n') break;
*cs = '\0';
if (c == EOF && (cs == s || ferror(iop))) return NULL;
return s;
```
1. `--n > 0`: 먼저 n을 줄이고 검사하니 최대 n−1번만 돌아요. 남은 한 칸은 `'\0'` 자리예요. 그래서 배열 크기를 n으로 주면 넘치지 않아요.
2. `(c = getc(iop)) != EOF`: 한 글자씩 받고, EOF면 멈춰요.
3. `*cs++ = c`로 먼저 저장한 뒤 `'\n'`인지 봐요. 저장이 먼저라서 개행이 문자열에 남아요.
4. 루프 밖에서 `'\0'`을 붙여 항상 문자열로 끝나게 해요.
5. EOF로 멈췄는데 한 글자도 못 읽었거나(`cs == s`) 오류였으면 `NULL`을 돌려줘요.

### gets는 왜 사라졌나

`char *gets(char *str);`는 stdin에서 개행까지 읽고, 개행은 저장하지 않고 `'\0'`으로 바꿔요 [A p25]. 문제는 배열 크기를 받지 않아 경계 검사를 못 한다는 거예요. 긴 줄이 들어오면 배열 뒤 메모리를 덮어쓰는 **버퍼 오버플로(buffer overflow)** 가 나요. 그래서 C11 표준에서 제거됐어요. `fgets`는 최대 개수를 지정하니 더 안전해요. 개행 처리도 달라서, `fgets`는 개행을 저장하고 `gets`는 저장하지 않아요.

### scanf의 함정과 남은 문자

`scanf("%s", buffer)`도 같은 위험이 있어요 [A p26]. `char buffer[10]`에 긴 단어를 넣으면 넘쳐요. 안전한 대안은 이래요.
```c
fgets(buffer, size, stdin);
scanf("%79s", buffer);       // buffer 크기가 80일 때
getline(&p, &cap, stdin);    // POSIX, char *p = NULL
```
폭을 제한하면 넘치지는 않지만, 다 못 읽은 글자는 입력 바구니에 남아 다음 입력 함수가 가져가요. 반복문으로 여러 번 읽으면 엉뚱한 값이 들어와 헷갈려요. C에는 입력 버퍼를 비우는 표준 함수가 없어서 직접 버려요.
```c
while ((ch = getchar()) != '\n' && ch != EOF) ;
```

### getline: 크기를 알아서 맞추는 줄 읽기

```c
ssize_t getline(char **lineptr, size_t *n, FILE *stream);
char *buffer = NULL; size_t size = 0;
len = getline(&buffer, &size, stdin);
free(buffer);
```
[A p27]
- `buffer`가 `NULL`이면 `malloc`으로 알맞은 크기를 잡고, 크기를 `size`에, 주소를 `buffer`에 넣어요.
- 끝의 `'\n'`까지 한 줄을 통째로 읽어요(EOF로 끝난 줄이면 개행 없이).
- 줄이 버퍼보다 길면 다시 할당하고 `size`를 갱신해요.
- 반환값은 개행을 포함하고 `'\0'`은 뺀 글자 수, 아무것도 못 읽었거나 오류면 −1이에요. `ssize_t`는 −1을 담을 수 있는 부호 있는 크기 형이에요(POSIX).
- −1이 나와도 이미 버퍼를 할당했을 수 있으니 **항상** `free(buffer)` 해요.
- `getline`은 표준 C가 아니라 POSIX(Linux, macOS 같은 Unix 계열이 공유하는 표준) 함수예요. Windows의 MSVC에는 없어요.

### fputs와 puts

```c
int fputs(const char *s, FILE *iop);
```
구현은 `while (c = *s++) putc(c, iop);`로 `'\0'`을 만날 때까지 한 글자씩 쓰고, `ferror(iop) ? EOF : 0`을 돌려줘요 [A p28]. 그래서 성공하면 음이 아닌 값, 오류면 `EOF`예요.

`puts(str)`는 stdout에 쓰고 **개행을 자동으로 붙여요**. `fputs(str, stream)`은 아무 스트림에나 쓸 수 있고 **개행을 붙이지 않아요** [A p29]. `fgets`가 개행을 남기니, `fgets`로 읽은 줄은 `fputs`로 그대로 쓰면 줄 모양이 맞아요.

**예제: fgets와 fputs** [A p30]. `input.txt`의 첫 줄을 읽어 화면과 `output.txt`에 써요. 판단 순서만 보면 이래요.
1. 입력 파일 열기 실패 → `perror("Error opening input file")`.
2. 출력 파일 열기 실패 → 입력 파일을 닫고 종료.
3. `fgets(...) == NULL`이면 `ferror(inputFile)`로 갈라요. 참이면 "Read error", 거짓이면 EOF이므로 "Empty file"을 stderr에 써요.
4. 성공하면 `fputs(buffer, stdout)`과 `fputs(buffer, outputFile)`.

`perror`는 stderr로 출력하므로 `./a.out 2> err.txt`로 실행하면 화면에는 아무것도 안 나오고 메시지는 err.txt에 저장돼요.

일기 중간의 특정 날짜로 바로 건너뛰고 싶다면 어떻게 할까요?

## 12. 임의 접근: fseek, rewind

공책에는 "지금 읽는 위치"를 가리키는 책갈피(위치 표시자)가 있어요. 이걸 옮기는 함수가 `fseek`이에요 [A p31].
```c
int fseek(FILE *stream, long offset, int whence);
```
- `whence`("어디로부터"): `SEEK_SET` 파일 처음, `SEEK_CUR` 현재 위치, `SEEK_END` 파일 끝. 예를 들어 `fseek(fp, -5, SEEK_END)`는 끝에서 5바이트 앞이에요.
- `offset`: 바이너리 스트림이면 `whence`에서 떨어진 바이트 수예요. 텍스트 스트림이면 0이나 `ftell`이 알려 준 값만 써야 해요.
- 성공하면 0, 실패하면 0이 아닌 값을 돌려줘요.

**예제** [A p32]. `example.txt`의 내용이 `0123456789Hello, fseek!`일 때
1. `"rb"`로 열어요. 바이너리 모드라야 오프셋이 정확한 바이트 수로 유지돼요. Windows 텍스트 모드는 `\r\n`을 `\n`으로 바꿔서 바이트 수가 어긋날 수 있어요.
2. `fseek(file, 10, SEEK_SET)`: 처음부터 세니 0~9번 바이트를 건너뛰고, 다음 읽기는 10번 바이트 `'H'`부터예요.
3. `fgetc` 루프로 끝까지 출력 → `Hello, fseek!`
4. 끝나면 `ferror`로 읽기 오류를 확인해요.

**rewind** [A p33].
```c
void rewind(FILE *stream);
```
책갈피를 맨 처음으로 옮겨요. `fseek(stream, 0L, SEEK_SET)`과 같은데, 하나가 더 있어요. 스트림마다 읽기·쓰기 오류가 나면 켜지는 오류 표시자가 있는데, `rewind`는 이것도 **꺼요**. 그래서 이후 `ferror`는 0을 돌려줘요. 대신 반환값이 없어서 실패를 알려 주지 못해요. 이미 한 번 처리한 파일을 처음부터 다시 볼 때 써요.

책갈피를 옮길 줄 알았으니, 4절에서 미뤄 둔 갱신 모드 규칙을 풀 수 있어요.

## 13. 갱신 모드에서 읽기와 쓰기 바꾸기

`r+`, `w+`, `a+`는 읽기와 쓰기가 **바구니 하나, 책갈피 하나**를 함께 써요 [A p10, p34]. 쓰기 직후에는 바구니에 아직 창고로 안 간 글자가 있고, 읽기 직후에는 바구니에 미리 당겨 온 글자가 있어요. 이 상태에서 방향을 바꾸면 낡은 바구니 내용을 읽거나 엉뚱한 위치에 쓰게 돼요. 이건 미정의 동작(undefined behavior)이에요. 그래서 규칙이 있어요.
- 쓰기 → 읽기: 먼저 `fflush`, `fseek`, `rewind` 중 하나
- 읽기 → 쓰기: 먼저 `fseek`이나 `rewind` (EOF에 있지 않다면)

**예제** [A p34]. `"w+"`로 `data.txt`를 열면 빈 파일이 생겨요.
```c
fputs("hello\n", fp);      // 쓰기
rewind(fp);                // 쓰기→읽기 전환
int c = fgetc(fp);         // 'h'
fseek(fp, 0L, SEEK_SET);   // 읽기→쓰기 전환
fputc('J', fp);            // 'h'를 'J'로
rewind(fp);                // 다시 쓰기→읽기
fgets(line, sizeof line, fp);
```
출력은 `first char: h`, `after update: Jello`예요. 전환마다 책갈피를 옮기는 호출이 바구니를 정리해 줬기 때문에 정확한 자리에 `J`가 들어갔어요.

여기까지는 바구니를 도우미가 관리해 줬어요. 이제 바구니 없이 창고지기에게 직접 가 볼게요.

# Part 2. 시스템 호출 입출력

## 14. 시스템 호출이란

**시스템 호출(system call)** 은 프로그램이 운영체제 커널에 서비스를 요청하는 일이에요 [A p36]. 창고지기에게 "공책 열어 주세요", "50바이트 읽어 주세요"라고 직접 부탁하는 거예요. `open()`, `read()`, `write()`, `close()`가 파일에 직접 닿는 시스템 호출이에요.

GNU/Linux의 층을 위에서 아래로 보면 사용자 공간에 사용자 응용 프로그램과 GNU C 라이브러리(glibc)가 있고, 커널 공간에 시스템 호출 인터페이스, 커널, 아키텍처 의존 커널 코드가 있고, 맨 아래에 하드웨어 플랫폼이 있어요.

> 보충: stdio 함수도 결국 glibc 안에서 시스템 호출 인터페이스를 거쳐 커널에 닿아요(18절의 `fgetc` 구현에서 확인할 수 있어요).

시스템 호출은 stdio 바구니를 건너뛰어요. 하지만 창고지기는 여전히 자기 임시 선반, **페이지 캐시**에 데이터를 둬요. `fopen`보다 세밀한 제어(플래그, 권한)를 할 수 있는 대신, 바구니는 **직접** 만들어야 해요. 안 만들면 작은 호출이 잔뜩 생겨 느려져요.

**stdio와 비교** [A p37].
- 손잡이: stdio는 `FILE *`, 시스템 호출은 `int` 파일 디스크립터예요.
- 버퍼: stdio는 사용자 공간 바구니가 있고, 시스템 호출은 없어요(커널 캐시는 있음).
- 이식성: stdio는 ISO C라 어디서나 되고, 시스템 호출은 POSIX/Unix/Linux에 묶여요.
- 편의성: stdio는 서식·줄 입출력이 쉽고, 시스템 호출은 원시 바이트만 다뤄요.
- 성능: 작은 읽기·쓰기가 많으면 stdio가 빠르고, 크고 잘 통제된 입출력은 시스템 호출이 더 빠를 수 있어요.
- 오류 확인: stdio는 `ferror`, `feof`, 시스템 호출은 −1을 돌려주고 `errno`를 설정해요.
- 텍스트/바이너리: stdio는 Windows 텍스트 모드에서 파일의 `"\r\n"`을 메모리의 `"\n"`으로, 메모리의 `"\n"`을 파일의 `"\r\n"`으로 바꿀 수 있어요. 시스템 호출은 항상 원시 바이트예요.
- 고급 입출력(논블로킹, 비동기, 폴링): stdio는 지원하지 않고, 시스템 호출은 `select`, `poll`, `epoll`, `O_NONBLOCK` 등으로 지원해요.

창고지기는 공책을 이름이 아니라 번호표로 기억해요. 그 번호표가 무엇일까요?

## 15. 파일 디스크립터와 read, write

**파일 디스크립터(file descriptor, fd)** 는 운영체제가 열린 파일을 구별하는 음이 아닌 정수, 즉 번호표예요 [A p38]. 0은 표준 입력, 1은 표준 출력, 2는 표준 오류예요. 9절 리다이렉션의 `2>`가 바로 이 번호예요.

```c
#include <unistd.h>
ssize_t read(int fd, void *buf, size_t n);
ssize_t write(int fd, const void *buf, size_t n);
```
- 반환값은 실제로 옮긴 바이트 수이고, n보다 **적을 수 있어요**.
- `read`는 파일 끝에서 **0**을 돌려줘요.
- 둘 다 오류면 **−1**이에요.

`size_t`는 "size type", `ssize_t`는 부호 있는 `size_t`예요. −1을 담아야 하니 부호가 필요해요. `size_t`의 실제 형은 데이터 모델에 따라 달라요.
- ILP32(32비트 Linux): int·long·포인터 모두 32비트, `size_t`는 `unsigned int`
- LP64(64비트 Linux/macOS): int 32, long·포인터 64, `unsigned long`
- LLP64(64비트 Windows): int·long 32, 포인터 64, `unsigned long long`

번호표를 받으려면 먼저 공책을 열어야겠죠?

## 16. open, creat, close

```c
#include <fcntl.h>
int open(const char *path, int oflag, ... /* mode_t mode */);
int creat(const char *path, mode_t mode);
```
[A p39] `oflag`에는 플래그를 `|`로 묶어 줘요.
- `O_RDONLY` 읽기 전용, `O_WRONLY` 쓰기 전용, `O_RDWR` 읽기·쓰기
- `O_APPEND` 쓰기는 항상 파일 끝에
- `O_CREAT` 없으면 만들기
- `O_TRUNC` 있는 파일을 길이 0으로 자르기
- `O_EXCL` `O_CREAT`와 함께 쓰면 파일이 이미 있을 때 실패

세 번째 `mode`는 새로 만들 파일의 권한이에요. `O_CREAT`가 없으면 무시되니 `open(name, O_RDONLY, 0)`처럼 0을 주거나 생략해요. `creat(path, mode)`는 `open(path, O_WRONLY|O_CREAT|O_TRUNC, mode)`와 같아요. 그래서 기존 파일을 **잘라 버려요**. 실패하면 둘 다 −1이에요.

**예제** [A p40]. `open("file.txt", O_RDONLY)` → `fd == -1`이면 `perror` → `read(fd, buffer, sizeof(buffer))` → 읽은 게 있으면 `write(1, buffer, bytesRead)`로 화면에 → `close(fd)`.

**예제: cp** [A p43]. 핵심 줄은 이래요.
```c
#define PERMS 0666
f1 = open(argv[1], O_RDONLY, 0);
f2 = creat(argv[2], PERMS);
while ((n = read(f1, buf, BUFSIZ)) > 0)
    if (write(f2, buf, n) != n) error("cp: write error on file %s", argv[2]);
```
1. 원본을 읽기로 열어요. 실패하면 `error`로 끝내요.
2. 대상을 권한 0666(소유자·그룹·기타 모두 읽기·쓰기)으로 만들어요.
3. `BUFSIZ`만큼씩 읽고, 읽은 만큼 써요. 쓴 양이 n과 다르면 오류예요.
4. 둘 다 닫아요.

여기서 세 가지를 짚어요.
- `BUFSIZ`는 `<stdio.h>`의 매크로로, `printf`, `scanf`, `fread`, `fwrite` 같은 스트림 함수가 쓰는 버퍼 크기예요. 512, 1024, 2048, 4096바이트 등 구현마다 달라요.
- 파일은 실제로 `PERMS & ~umask` 권한으로 만들어져요. umask가 022면 0666이 0644가 돼요.
- `read`가 −1을 돌려줘도 `> 0` 조건이 거짓이 되어 루프가 **조용히** 끝나요. 튼튼하게 만들려면 루프 뒤에 `n < 0`을 검사해 오류를 알려야 해요.

## 17. 오류 출력 함수 error: 가변 인자

cp의 `error`는 `printf`처럼 인자 개수가 바뀌어요 [A p44].
```c
void error(char *fmt, ...) {
    va_list args;
    va_start(args, fmt);
    fprintf(stderr, "error: ");
    vfprintf(stderr, fmt, args);
    fprintf(stderr, "\n");
    va_end(args);
    exit(1);
}
```
1. `va_list args`: `...` 자리의 인자들을 하나로 묶어 들고 다닐 변수예요.
2. `va_start(args, fmt)`: `fmt` 다음부터의 인자를 `args`로 꺼낼 수 있게 초기화해요.
3. `vfprintf`: 인자 목록 대신 `va_list`를 받는 `printf`예요.
4. `va_end`로 정리하고 `exit(1)`로 끝내요.

이제 바구니가 없을 때 정말 느린지, 직접 만들어 볼까요?

## 18. 바구니 직접 만들기: my_getchar

**입력을 출력으로 복사** [A p41].
```c
while ((n = read(0, buf, BUFSIZ)) > 0) write(1, buf, n);
```
fd 0에서 읽어 fd 1로 써요. 한 번에 `BUFSIZ`씩 옮기니 호출 횟수가 적어요.

**바구니 없는 한 글자 읽기** [A p41].
```c
return (read(0, &c, 1) == 1) ? (unsigned char)c : EOF;
```
한 글자마다 창고지기를 불러요. 한 바이트를 읽으면 그 글자를, 아니면 EOF를 돌려줘요.

> 보충: `(unsigned char)`로 바꾸면 바이트 값이 음수가 되지 않아 EOF와 헷갈리지 않아요.

**바구니 있는 한 글자 읽기** [A p42]. `static` 변수 세 개가 바구니(`buf[BUFSIZ]`), 다음에 꺼낼 위치(`bufp`), 남은 개수(`n`)를 함수 호출 사이에 기억해요.
1. `n == 0`이면 바구니가 비었으니 `read(0, buf, sizeof buf)`로 채워요.
2. `n >= 0`이면 성공이에요. `errno == EINTR`이면 시그널 때문에 중간에 끊긴 것이니 다시 시도해요(핸들러가 SA_RESTART 없이 설정된 경우). 그 밖의 오류면 `n = 0`으로 되돌려 다음 호출에 대비하고 EOF를 돌려줘요.
3. `bufp`를 바구니 처음으로 돌리고, 읽은 게 0바이트면 진짜 EOF예요.
4. `n--` 하고 `*bufp++`를 돌려줘요.

**errno** 는 `<errno.h>`의 매크로로, C11부터 스레드마다 하나씩 있어요. 라이브러리나 시스템 호출이 실패하면 어떤 오류였는지 여기에 적어 둬요.

이건 사실 stdio의 `fgetc`가 하는 일과 같아요. 간단히 쓴 `fgetc`도 `stream->cnt == 0`이면 `read(stream->fd, stream->buf, BUFSIZ)`로 채우고 `stream->ptr`에서 하나씩 꺼내요(EOF나 오류 뒤에는 `cnt`가 음수로 남는 단순화된 판이에요). 5절에서 말한 FILE 구조체 속 fd와 버퍼가 이렇게 쓰여요.

필요 없는 공책은 어떻게 버릴까요?

## 19. unlink: 파일 지우기

```c
#include <unistd.h>
int unlink(const char *pathname);
```
[A p45] 성공하면 0, 실패하면 −1을 돌려주고 errno를 설정해요. 예제는 `unlink("old_file.txt") == -1`이면 `perror`를 불러요.

이름이 "delete"가 아니라 "unlink"인 이유가 있어요. 이 호출은 디렉터리에서 파일 이름 항목(디렉터리 엔트리)을 떼어낼 뿐이에요. 실제 데이터 블록은 다른 하드 링크가 남아 있지 않고, 그 파일을 열어 둔 프로세스도 없을 때 비로소 풀려요.

토리의 일기가 정전에도 살아남으려면 무엇이 더 필요할까요?

## 20. fsync, fdatasync: 진짜 창고에 넣기

**문제.** `write()`가 끝났다고 데이터가 디스크에 있는 건 아니에요 [A p46]. 창고지기의 임시 선반(페이지 캐시)에 올라가 있을 뿐이고, 커널은 나중에 디스크에 써요. 그 사이에 전원이 나가면 사라져요. 데이터베이스나 로그처럼 꼭 남아야 하는 데이터에는 곤란해요.

**해결.** 두 호출은 데이터가 디스크에 물리적으로 저장될 때까지 기다려요.
```c
int fsync(int fd);       // 데이터 + 모든 메타데이터(크기, 타임스탬프)
int fdatasync(int fd);   // 데이터 + 읽는 데 필요한 메타데이터만(예: 새 크기)
```
`fdatasync`는 내용만 바뀌었다면 타임스탬프 갱신을 건너뛰어 디스크 쓰기를 한 번 줄여요.

**주의.** 둘 다 stdio 바구니는 비우지 않아요. `FILE *`로 썼다면 `fflush(fp)`로 바구니를 선반까지 보낸 다음 `fsync(fileno(fp))`로 창고까지 넣어요. 데이터의 길은 이렇게 이어져요: 바구니 →(fflush/fclose/exit)→ 선반 →(fsync)→ 창고.

**예제** [A p47].
```c
fd = open("log.txt", O_WRONLY | O_CREAT | O_APPEND, 0644);
write(fd, "Important log entry\n", 20);
if (fsync(fd) == -1) { perror("Error syncing file"); close(fd); return 1; }
```
없으면 만들고(권한 0644), 항상 끝에 덧붙이고, 디스크에 들어갈 때까지 기다려요.

마지막으로, 바구니 없이도 원하는 자리로 바로 갈 수 있을까요?

## 21. lseek: 번호표로 책갈피 옮기기

```c
#include <unistd.h>
off_t lseek(int fd, off_t offset, int whence);
long lseek(int fd, long offset, int origin);   /* K&R, 옛 형태 */
```
[A p48] 데이터를 읽거나 쓰지 않고 위치만 옮겨요. `whence`는 `fseek`과 같은 뜻인데 숫자 값도 함께 기억해 둬요. `SEEK_SET`(0)은 처음부터, `SEEK_CUR`(1)은 현재 위치부터, `SEEK_END`(2)는 끝부터 재요.
```c
lseek(fd, 0L, SEEK_END);   // 끝으로
lseek(fd, 0L, SEEK_SET);   // 처음으로
```

**예제: pos에서 n바이트 읽기** [A p49].
```c
if (lseek(fd, pos, SEEK_SET) >= 0) return read(fd, buf, n);
else return -1;
```
1. 처음에서 `pos`만큼 떨어진 곳으로 옮기고, 반환값이 `>= 0`인지 검사해요.
2. 성공했으면 그 자리에서 읽고, 실패했으면 −1을 돌려줘요.

> 보충: `lseek`은 성공하면 이동한 뒤의 새 위치(0 이상)를 돌려줘요. 그래서 `>= 0`으로 성공을 판단해요.

이제 토리는 일기를 저장하고(지속성), 고치고(갱신 모드), 원하는 날짜로 건너뛰고(fseek, lseek), 정전에도 지킬 수 있어요(fsync).

## 한눈에 이어 보기

- 변수는 사라짐 → 파일(텍스트/바이너리) → `fopen`(모드) → `FILE *` → 스트림과 버퍼(바구니)
- 바구니로 읽고 쓰기: 문자(`getc`, EOF) → 서식(`fscanf`) → 줄(`fgets`, `getline`, `fputs`) → 위치(`fseek`, `rewind`) → 갱신 모드 전환 규칙
- 표준 스트림 stdin/stdout/stderr → fd 0/1/2 → 리다이렉션 → 오류는 stderr, 끝은 `exit`(플러시)
- 바구니 없이 창고지기에게 직접: 시스템 호출 → fd → `open`/`creat` → `read`/`write` → 직접 버퍼링(`my_getchar` = `fgetc`의 속)
- 관리: `unlink`(이름 떼기) → `fsync`/`fdatasync`(선반에서 창고로) → `lseek`(위치 이동)
