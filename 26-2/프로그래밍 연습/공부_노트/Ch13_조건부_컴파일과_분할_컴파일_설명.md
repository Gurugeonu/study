## 이야기의 시작: 워드프로세서를 만드는 팀

민지네 팀은 `WordProcessor`라는 문서 편집 프로그램을 만들고 있어요. 편집기, 맞춤법 검사기, 서식 기능을 서로 다른 사람이 맡았어요. 이 단원은 이 팀이 차례로 부딪히는 문제들을 따라가요.

- 같은 코드로 Windows판과 Linux판, 개발용과 출시용을 만들고 싶다 → **조건부 컴파일**
- 저장할 문서 정보를 구조체에 담았더니 크기가 예상과 다르다 → **패딩과 정렬, union**
- 파일이 여러 개로 늘어나자 어떻게 묶어야 할지 막막하다 → **분할 컴파일, make, 중복 정의, extern/static**

이 단원의 학습 목표도 이 순서와 같아요. 조건부 컴파일, 구조체의 패딩과 정렬, union, 분할 컴파일, 중복 정의, extern과 static이에요 [A p48].

## 1. 조건부 컴파일: 코드에 붙이는 "이 부분은 건너뛰세요" 쪽지

**왜 필요할까요?** 민지는 디버깅할 때만 상태를 출력하고 싶고, Windows와 Linux에서 다르게 동작하는 코드도 써야 해요. 파일을 두 벌로 만들면 하나를 고칠 때 다른 쪽을 빠뜨리기 쉬워요.

**직관:** 연극 대본에 "서울 공연이면 이 대사, 부산 공연이면 저 대사"라는 쪽지를 붙여 두는 것과 같아요. 배우(컴파일러)가 무대에 오르기 전에 연출가(전처리기)가 쪽지대로 대본을 잘라 줘요. 이 "대본 자르기" 비유를 단원 끝까지 이어 쓸게요.

**정의:** 조건부 컴파일(conditional compilation)은 전처리 단계에서 정해 둔 조건에 따라 코드 일부를 컴파일하거나 무시하는 C의 기능이에요. 이식성 있는 코드를 쓰거나 디버깅할 때 유용해요 [A p2].

지시자는 다음과 같아요 [A p2].

- `#if 상수식`: 상수식이 참(0이 아님)이면 블록을 컴파일해요. `defined(NAME)`으로 매크로가 있는지 물어볼 수 있어요.
- `#ifdef NAME`은 매크로가 정의돼 있으면, `#ifndef NAME`은 정의돼 있지 않으면 컴파일해요.
- `#else`는 앞 조건이 안 맞을 때의 대체 블록이고, `#elif`는 else와 if를 합친 거예요.
- `#elifdef`, `#elifndef`(C23)는 `#elif defined`, `#elif !defined`를 줄여 쓴 거예요.
- `#endif`는 `#if`, `#ifdef`, `#ifndef` 블록을 닫아요.

가장 짧은 예는 "PI가 아직 없으면 만들어라"예요.

```c
#if !defined(PI)
#define PI 3.14159
#endif
```

**자주 쓰는 모습** [A p3]: 디버깅 코드와 플랫폼별 코드, 버전 비교예요.

```c
#ifdef DEBUG          // DEBUG가 정의됐을 때만
printf("Debug Information\n");
#endif

#ifdef WINDOWS
// Windows 전용 코드
#elif defined LINUX
// Linux 전용 코드
#else
// 그 밖의 플랫폼
#endif

#if (VER >= 3)        // 괄호는 생략해도 돼요: #if VER >= 3
max = 1;
#else
max = 1.0;
#endif
```

**장점과 한계** [A p3]: 환경마다 다른 코드를 관리하기 쉬워지고, 모든 변형을 한 코드베이스에 둘 수 있어요. 필요 없는 코드는 아예 컴파일하지 않으니 컴파일 시간도 줄어요. 다만 쪽지를 너무 많이 붙이면 대본을 읽기 어려워져요. 과용하면 가독성이 떨어져요.

그런데 이번엔 이 쪽지로 "개발할 때만 검사하고, 출시할 때는 검사를 빼는" 장치를 만들면 어떻게 될까요?

## 2. assert와 NDEBUG: 개발용 검문소

**왜 필요할까요?** 민지의 나눗셈 함수에 0이 들어오면 프로그램이 망가져요. 개발 중에는 바로 멈춰서 알려 주면 좋지만, 출시판에서는 검사 비용을 없애고 싶어요.

**정의:** `<assert.h>`의 `assert`는 조건부 컴파일로 만든 매크로예요. 단순화한 모습은 이래요 [A p4].

```c
#ifdef NDEBUG
#define assert(cond) ((void)0)
#else
#define assert(cond) \
    ((cond) ? (void)0 \
            : report(#cond, __FILE__, __LINE__, __func__))
#endif
```

한 줄씩 읽어 볼게요.

1. `NDEBUG`가 정의돼 있으면 `assert(cond)`는 `((void)0)`, 곧 아무것도 안 하는 식으로 바뀌어요. 검문소를 통째로 치우는 거예요.
2. 정의돼 있지 않으면 조건이 참일 때는 아무것도 안 하고, 거짓일 때만 `report`를 불러요.
3. `#cond`는 조건식을 문자열로 바꾸고, `__FILE__`, `__LINE__`, `__func__`는 어디서 실패했는지 알려 줘요. 이 매크로들은 5절에서 다시 봐요.

**적용** [A p4]: `divide`에 `assert(b != 0);`을 넣었다고 해 봐요.

- 디버그 빌드 `gcc main.c -o app`: `app: main.c:4: divide: Assertion 'b != 0' failed.`를 출력하고 멈춰요.
- 릴리스 빌드 `gcc -DNDEBUG main.c -o app`: 모든 assert가 사라져요. `divide(1, 0)`은 검사 없이 실행돼서 프로그램이 죽거나 쓰레기값을 돌려줘요.

`-DNDEBUG`는 컴파일 명령에서 매크로 `NDEBUG`를 정의하는 옵션이에요. 분할 컴파일에서 기능 플래그를 켤 때 같은 방식을 또 써요.

**주의:** 꼭 실행돼야 하는 일을 assert 안에 넣으면 안 돼요. `assert(init() == 0)`은 릴리스 빌드에서 `init()` 호출 자체가 사라져요.

그런데 이번엔 조건이 맞지 않을 때 실행 중이 아니라 **컴파일 단계에서** 바로 멈추게 하려면 어떻게 할까요?

## 3. #error, #warning, #pragma: 연출가에게 남기는 다른 메모들

**#error** [A p5]: 전처리 중에 오류 메시지를 출력하고 컴파일을 멈춰요. 형식은 `#error 메시지`이고, 예를 들면 `#error "Version not supported"`예요. 민지 팀은 버전이 낮은 컴파일러를 막을 때 썼어요.

```c
#if VER >= 3
max = 1;
#else
#error Compiler version should be 3 or higher   // 출력하고 멈춤
#endif
```

**#warning** [A p6]: 경고만 출력하고 컴파일은 계속돼요. 형식은 `#warning 메시지`예요. C23부터 표준이 되었고, 그 전에는 GCC/Clang 확장이었어요.

```c
#ifdef USE_OLD_API
#warning USE_OLD_API is deprecated   // 출력하고 계속 진행
#endif
```

`#error`는 "공연 중단", `#warning`은 "주의하고 계속"이라고 기억하면 돼요.

**#pragma** [A p7, p8]: 컴파일러에게 추가 정보를 주는 특수 지시자예요. `#pragma`라는 지시자 자체는 C와 C++ 표준에 있지만, 각 pragma가 무엇을 하는지는 구현 정의(implementation-defined)예요. 컴파일러는 모르는 pragma를 그냥 무시해요.

- C 표준 pragma는 부동소수점 동작을 다뤄요. C99에는 `FP_CONTRACT`, `FENV_ACCESS`, `CX_LIMITED_RANGE`가 있고, C23에서 `FENV_ROUND`, `FENV_DEC_ROUND`가 추가됐어요. `#pragma STDC FENV_ACCESS ON`을 쓰면 그 뒤 코드가 반올림 모드를 바꾸거나 부동소수점 예외 플래그를 검사할 수 있다고 알려 주는 거예요.
- 대부분의 pragma는 표준이 아니라 컴파일러 확장이에요. MSVC에서는 `#pragma warning(disable : 4446)`로 경고 C4446을 끄고, `#pragma optimize("", off)`와 `#pragma optimize("", on)` 사이에 둔 코드는 최적화하지 않아요.

그런데 이번엔 pragma로 **구조체가 메모리에 놓이는 방식**까지 바꿀 수 있다면 어떻게 될까요?

## 4. 구조체 패딩과 정렬: 4칸짜리 선반에 물건 놓기

**왜 필요할까요?** 민지는 `{char a; int b;}` 구조체가 1 + 4 = 5바이트일 거라 생각했는데, `sizeof`를 찍어 보니 8바이트였어요 [A p9].

**직관:** 메모리를 4칸(또는 8칸)씩 나뉜 선반이라고 생각해 봐요. CPU는 물건을 꺼낼 때 선반 한 줄을 통째로 가져와요. `int`처럼 4칸짜리 물건이 두 줄에 걸쳐 있으면 두 번 꺼내야 해요. 그래서 컴파일러는 물건이 줄 경계에 걸치지 않도록 빈칸, 곧 **패딩(padding)** 을 끼워 넣어요.

**정의** [A p12]: 바이트 정렬(byte alignment)은 데이터 멤버에 효율적으로 접근하도록 메모리에 배치하는 방식이에요. 구조체를 정의하면 컴파일러가 멤버 사이에 패딩 바이트를 넣을 수 있어요. 정렬하면 접근은 빨라지지만 메모리를 더 써요. 패딩을 막는 packed 속성도 있지만 많은 아키텍처에서 느려질 수 있어요.

**#pragma pack으로 비교하기** [A p9–p11]

```c
#pragma pack(push, 1)   // 패킹 정렬을 1바이트로
typedef struct { char a; int b; } CompactStruct;
#pragma pack(pop)       // 이전 정렬로 복원
typedef struct { char a; int b; } RegularStruct;
```

- 기본적으로 컴파일러는 멤버를 자연 경계(4 또는 8바이트)에 맞춰요. 그래서 `RegularStruct`는 `a`(offset 0) 뒤에 패딩 3바이트를 두고, `b`를 offset 4에 놓아 **8바이트**가 돼요.
- `CompactStruct`는 패딩이 없어서 **5바이트**예요. 대신 `b`가 offset 1에서 시작해 4바이트 경계를 넘어가요. CPU는 `b`를 읽으려고 두 번 접근해야 해요.
- 그래서 packed 구조체는 느릴 수 있어요. 어떤 CPU는 정렬되지 않은 접근에서 아예 오류(fault)를 내요. 꼭 필요할 때만 써야 해요.
- 패딩과 정렬은 C 표준에서 구현 정의이고, `#pragma pack`도 표준이 아니에요. MSVC, GCC, Clang이 확장으로 지원할 뿐이에요.

**정렬 규칙(x86-64)** [A p13]

1. 각 멤버는 **자기 정렬의 배수 위치**에서 시작해요. `short`는 2, `int`는 4, `double`은 8이에요.
2. 구조체 전체 크기는 **가장 큰 멤버 정렬의 배수**예요. 그래서 끝에도 패딩이 붙을 수 있어요. 이걸 꼬리 패딩(tail padding)이라고 해요.
3. C는 선언 순서를 지켜요. 컴파일러가 멤버 순서를 바꾸지 않아요.

실제 배치는 아키텍처와 컴파일러 설정에 따라 달라질 수 있어요.

**예제: struct student의 크기** [A p13]

```c
struct student { char ch1; short num; char ch2; int score; double grade; char ch3; };
```

앞에서부터 선반에 놓아 볼게요.

1. `ch1`(1바이트): offset 0. 다음 빈자리는 1이에요.
2. `num`(short, 정렬 2): 1은 2의 배수가 아니라서 1바이트 패딩 후 offset 2에 놓여요. 2~3을 차지해요.
3. `ch2`(1바이트): offset 4에 놓여요.
4. `score`(int, 정렬 4): 5는 4의 배수가 아니라서 3바이트 패딩 후 offset 8이에요. 8~11을 차지해요.
5. `grade`(double, 정렬 8): 12는 8의 배수가 아니라서 4바이트 패딩 후 offset 16이에요. 16~23을 차지해요.
6. `ch3`: offset 24. 여기까지 25바이트예요.
7. 가장 큰 정렬은 `double`의 8이에요. 25를 8의 배수로 올리면 **32바이트**이고, 꼬리 패딩은 7바이트예요.

패딩을 모두 더하면 1 + 3 + 4 + 7 = 15바이트예요.

**순서만 바꿔도 줄어들어요** [A p14]: 큰 것부터 `grade, score, num, ch1, ch2, ch3` 순으로 선언하면 grade 0~7, score 8~11, num 12~13, ch1 14, ch2 15, ch3 16이에요. 17바이트를 8의 배수로 올리면 **24바이트**예요. 멤버는 같은데 패딩이 15바이트에서 7바이트로 줄었어요. 그러니 패딩을 줄이려면 정렬이 큰 멤버부터 선언하면 돼요.

**추측하지 말고 재기** [A p15]: `<stddef.h>`의 `offsetof(type, member)`는 멤버가 몇 번째 바이트에 있는지 알려 줘요. `size_t` 값은 `%zu`로 출력해요.

```c
printf("score = %zu\n", offsetof(struct student, score));   // 8
_Static_assert(sizeof(struct student) == 32, "layout");
```

같은 프로그램에서 size는 32, ch2는 4(num 바로 뒤), score는 8(앞에 패딩 3), grade는 16(앞에 패딩 4)으로 나와서 위의 계산과 맞아요. `_Static_assert`는 **컴파일할 때** 조건을 검사해요. 레이아웃이 바뀌어 조건이 거짓이 되면 빌드가 실패하고, 두 번째 인자의 메시지를 보여 줘요. 2절의 `assert`는 실행 중에 검사하고, `_Static_assert`는 컴파일 중에 검사한다는 점이 달라요.

그런데 이번엔 선반 한 칸에 **여러 물건을 번갈아** 넣는다면 어떻게 될까요?

## 5. union: 한 칸을 같이 쓰는 사물함

**왜 필요할까요?** 민지 팀은 메모리가 작은 기기용 버전도 만들어야 해요. 값이 정수일 때도, 실수일 때도, 문자열일 때도 있는데 동시에 쓰이지는 않아요. 셋 다 따로 자리를 잡으면 낭비예요.

**직관:** 선반 한 칸을 여러 사람이 같이 쓰는 사물함이라고 생각해 봐요. 새 물건을 넣으면 이전 물건은 밀려나요.

**정의** [A p16, p17]

- 공용체(union)는 구조체와 비슷하지만 **모든 멤버가 같은 주소에서 시작하는 같은 메모리**를 공유해요.
- 한 번에 한 멤버의 값만 유효해요. 마지막에 쓴 멤버만 의미 있는 값이고, 한 멤버에 쓰면 나머지는 덮어써져요.
- 크기는 가장 큰 멤버의 크기를 정렬 배수로 올린 값이에요. 예를 들어 `union { char c[5]; int i; }`는 5를 `int`의 정렬 4의 배수로 올려 **8바이트**예요.

**타입 퍼닝(type punning)** [A p16]: 한 멤버로 쓰고 다른 멤버로 읽으면 같은 바이트를 다른 타입으로 해석하게 돼요.

```c
union Data { int i; float f; char str[20]; };
union Data data;
data.i = 10;     printf("%d\n", data.i);   // 10
data.f = 220.5;  printf("%d\n", data.i);   // 1130135552, 220.5가 아님
```

`220.5`를 float로 저장한 비트를 `int`로 읽었기 때문에 `1130135552`가 나와요.

**쓰임새** [A p17]

- 메모리가 부족한 환경: 버퍼 하나를 여러 타입이 같이 써서 RAM을 아껴요.
- 타입 퍼닝: float의 비트를 int로 읽는 것처럼 같은 바이트를 다른 타입으로 봐요.
- 하드웨어 레지스터 매핑: 레지스터를 워드 전체로도, 비트 필드 단위로도 읽어요.

**예제: 장치 제어 레지스터** [A p18, p19]

```c
union DeviceControlRegister {
    unsigned int value;              // 레지스터 전체
    struct {
        unsigned int enable : 1;     // 장치 켜기
        unsigned int mode : 2;       // 모드
        unsigned int reserved : 13;  // 예약
        unsigned int error : 1;      // 오류
        unsigned int status : 15;    // 상태
    } fields;
};
reg.value = 0x2BAD;    // 전체를 한 번에 씀
reg.fields.mode = 3;   // 모드 비트만 바꿈
printf("0x%X\n", reg.value);   // 바뀐 전체 값 확인
```

`value`에 원시 값을 쓰고 `fields`로 비트를 하나씩 읽어요. 반대로 `mode`만 바꾼 뒤 `value`를 보면 전체 값이 어떻게 바뀌었는지 알 수 있어요.

**주의(이식성 없음)** [A p19]: 비트 필드는 선언 순서를 유지하지만, 첫 필드가 `value`의 하위 비트에 놓일지 상위 비트에 놓일지는 구현 정의예요. 그래서 출력값은 컴파일러마다 달라요.

> 보충: x86-64의 GCC처럼 첫 필드를 최하위 비트에 두는 경우 `0x2BAD`(2진수 `0010 1011 1010 1101`)에서 enable = 1, mode = 2, error = 0, status = 0이 되고, `mode = 3` 뒤의 값은 `0x2BAF`예요. 슬라이드에는 출력값이 없어요.

그런데 이번엔 assert가 썼던 `__FILE__`, `__LINE__` 같은 이름은 어디서 온 걸까요?

## 6. 미리 정의된 매크로: 대본에 자동으로 찍히는 도장

**정의** [A p20, p21]: 컴파일러가 미리 정의해 둔 매크로라서 따로 만들지 않아도 써요.

| 매크로 | 의미 | 예시 값 |
|---|---|---|
| `__FILE__` | 현재 소스 파일 이름 | `"example.c"` |
| `__LINE__` | 현재 줄 번호 | `15` |
| `__DATE__` | 컴파일한 날짜 | `"Mar 10 2023"` |
| `__TIME__` | 컴파일한 시각 | `"14:55:02"` |
| `__STDC__` | ANSI C 표준을 따르는지 | `1` |
| `__STDC_VERSION__` | 따르는 C 표준 버전 | `199901L`(C99) |
| `__cplusplus` | C++ 코드에서만 정의, C++ 버전 | `201103L`(C++11) |

`__func__`는 현재 함수의 이름이에요.

**적용** [A p20]: `example.c`의 `printDebugInfo` 함수 안 6번째 줄에서 `__FILE__`, `__func__`, `__LINE__`을 출력하면 `File: example.c`, `Function: printDebugInfo`, `Line: 6`이 나와요. `main`의 15번째 줄에서 같은 일을 하면 `File: example.c, Function: main, Line: 15`가 나와요. 매크로를 **쓴 자리**의 값이 찍힌다는 점이 중요해요. assert가 실패 위치를 정확히 알려 주는 것도 이 덕분이에요.

그런데 이번엔 팀의 코드가 파일 여러 개로 늘어나면 어떻게 될까요?

## 7. 분할 컴파일: 장면별로 따로 연습하고 마지막에 이어 붙이기

**왜 필요할까요?** 편집기, 맞춤법 검사기, 서식 코드를 파일 하나에 다 넣으면 한 줄만 고쳐도 전체를 다시 컴파일해야 해요. 여러 사람이 같은 파일을 고치다 부딪히기도 해요.

**직관:** 연극을 장면별로 따로 연습하고 마지막 리허설에서 이어 붙이는 거예요. 한 장면을 고치면 그 장면만 다시 연습하면 돼요.

**빌드 흐름** [A p23]

1. **전처리기**: `#include`, `#define`, `#if`를 처리해요. `main.c`가 `main.i`가 돼요. 1~6절의 대본 자르기가 이 단계예요.
2. **컴파일러**: **한 번에 파일 하나씩** 기계어로 바꿔요. `main.i`가 `main.o`(목적 파일)가 돼요.
3. **링커**: 여러 `.o` 사이의 이름(심볼)을 이어 붙여 실행 파일 `word_processor`를 만들어요.

**오류도 두 종류예요** [A p23]

- **컴파일 오류**는 파일 하나 안에서 발견돼요. 문법 오류, 선언되지 않은 이름, 한 파일 안에서 두 번 정의한 타입이 여기에 속해요.
- **링크 오류**는 파일 사이에서 발견돼요. 함수나 전역 변수를 두 번 정의했거나, 아예 정의하지 않았을 때(`undefined reference`) 생겨요.

**분할 컴파일의 이유:** `.c` 하나를 바꾸면 그 파일만 다시 컴파일하고, 링커는 나머지 `.o`를 그대로 다시 써요.

그런데 컴파일러가 파일을 하나씩만 본다면, `main.c`는 다른 파일에 있는 함수를 어떻게 알까요?

## 8. 선언과 정의, 그리고 헤더

**정의** [A p24]: **선언(declaration)** 은 "이런 이름이 있다"고만 알려요. **정의(definition)** 는 실체, 곧 메모리나 함수 본문을 만들어요.

- 함수: `void printDocument(Document d);`는 선언이고, 중괄호 본문이 붙으면 정의예요.
- 전역 변수: `extern Config globalConfig;`는 선언이고, `Config globalConfig = { 50, ENGLISH };`는 정의예요.

**규칙:** 선언은 모든 파일에 반복해도 되지만, 정의는 프로그램 전체에서 **정확히 한 번**이어야 해요.

**어디에 둘까요?**

- `.h` 파일에는 선언, 타입, 매크로를 둬요. 그 헤더를 포함하는 모든 파일이 공유해요.
- `.c` 파일에는 정의를 둬요. 한 번 컴파일되어 자기만의 `.o`가 돼요.
- `struct`, `typedef` 같은 타입 정의는 메모리를 만들지 않으니 헤더에 둬요. 대신 include guard로 보호해요(11절).

**민지 팀의 구성** [A p25, p29]: 공유 타입 `Document`는 `document.h`에 두고, 모듈마다 헤더(`document_editor.h`, `spell_checker.h`, `formatting.h`)와 `.c`를 하나씩 만들어요. 모듈 헤더는 모두 `document.h`를 포함하므로, 그 헤더를 포함한 `.c`는 `Document`를 쓸 수 있어요. `main.c`는 세 모듈 헤더를 포함하고 모듈마다 함수 하나(`editDocument`, `spellCheckDocument`, `formatDocument`)를 불러요. 그런데 이러면 `main.c`에 `document.h`가 세 번 들어와요. 이 문제는 11절에서 해결해요.

```c
// document_editor.h
#ifndef DOCUMENT_EDITOR_H
#define DOCUMENT_EDITOR_H
#include "document.h"
void editDocument(Document doc);   // 프로토타입만
#endif
```

**기능 플래그** [A p26–p28]: 각 모듈은 선택 기능을 조건부 컴파일로 감싸요. 정의와 호출을 **같은 플래그**로 감싸는 게 핵심이에요. 플래그 없이 빌드하면 함수도, 그 호출도 함께 빠져요.

```c
// document_editor.c
#if defined(FEATURE_ADVANCED_EDITING)
void advancedEditingFeature() { /* 고급 편집 */ }
#endif
void editDocument(Document doc) {
#if defined(FEATURE_ADVANCED_EDITING)
    advancedEditingFeature();
#endif
}
```

`spell_checker.c`는 `FEATURE_SPELLCHECK_LANG_SUPPORT`로, `formatting.c`는 `FEATURE_TEXT_STYLES`로 같은 패턴을 써요.

**손으로 빌드하기** [A p30]: 파일마다 `-c`로 컴파일만 하고, 마지막에 링크해요.

```sh
gcc -DFEATURE_ADVANCED_EDITING -DFEATURE_SPELLCHECK_LANG_SUPPORT \
    -DFEATURE_TEXT_STYLES -c document_editor.c -o document_editor.o
# spell_checker.c, formatting.c, main.c도 같은 방식으로
gcc main.o document_editor.o spell_checker.o formatting.o -o word_processor
```

`-DNAME`은 `NAME`을 정의해서 `#if defined(NAME)` 안의 코드를 켜요 [A p31]. 2절의 `-DNDEBUG`와 같은 원리예요.

그런데 이번엔 파일이 수십 개라면, 이 긴 명령을 매번 직접 쳐야 할까요?

## 9. Makefile과 make: 리허설 진행표

**정의** [A p31]: Makefile은 유닉스 계열 환경에서 빌드 과정을 관리하려고 만든 파일이에요. 실행할 작업들을 정의해 두면 컴파일과 링크가 간단해져요.

**변수** [A p31]

```make
CC=gcc
CFLAGS=-Wall -g -DFEATURE_ADVANCED_EDITING -DFEATURE_SPELLCHECK_LANG_SUPPORT -DFEATURE_TEXT_STYLES
SRCS=main.c document_editor.c spell_checker.c formatting.c
OBJS=$(SRCS:.c=.o)
MAIN=word_processor
```

`CC`는 컴파일러, `CFLAGS`는 컴파일 옵션과 기능 플래그예요. 그 밖에 `INCLUDES`(헤더 디렉터리), `LFLAGS`(`/usr/lib` 외 라이브러리 경로), `LIBS`(링크할 라이브러리)도 정의해요. `OBJS=$(SRCS:.c=.o)`는 파일 이름마다 `.c`를 `.o`로 바꿔 목적 파일 목록을 만들어요.

**규칙** [A p32]

```make
all: $(MAIN)
$(MAIN): $(OBJS)
	$(CC) $(CFLAGS) $(INCLUDES) -o $(MAIN) $(OBJS) $(LFLAGS) $(LIBS)
.c.o:
	$(CC) $(CFLAGS) $(INCLUDES) -c $< -o $@
clean:
	$(RM) *.o *~ $(MAIN)
```

- `$(MAIN): $(OBJS)`는 링크 단계예요. 모든 `.o`를 이어 프로그램을 만들어요.
- `.c.o:`는 접미사 규칙(suffix rule)이에요. 각 `.c`로 `.o`를 만들어요. `$<`는 `.c` 파일, `$@`는 `.o` 파일이에요.
- `depend: $(SRCS)` 규칙은 `makedepend $(INCLUDES) $^`로 헤더 의존성을 찾아 Makefile 끝에 적어요. `.PHONY: depend clean`도 함께 선언해요.

> 보충: `.PHONY`는 같은 이름의 파일이 있어도 그 규칙을 항상 실행하라는 표시이고, `$^`는 의존 파일 전체 목록이에요.

**사용법:** `make`는 전체 빌드, `make clean`은 `.o` 삭제, `make depend`는 `.h` 의존성 추가예요.

**make는 무엇을 다시 만들지 어떻게 정할까요?** [A p33] 규칙은 `타깃: 의존 파일` 다음 줄에 명령을 쓰는 형식이에요.

```make
spell_checker.o: spell_checker.c spell_checker.h document.h
	$(CC) -c spell_checker.c
```

make는 **의존 파일이 타깃보다 새로울 때만**(파일 타임스탬프 비교) 타깃을 다시 만들어요.

1. 처음 `make`를 실행하면 모든 `.c`를 컴파일하고 링크해요.
2. 아무것도 안 바꾸고 다시 실행하면 `make: 'word_processor' is up to date.`가 나와요.
3. `touch spell_checker.c`로 시각만 바꾸고 실행하면 `cc -c spell_checker.c`와 링크만 다시 해요.

7절에서 말한 "바뀐 장면만 다시 연습"을 make가 자동으로 해 주는 거예요.

**주의:** 의존 파일에 `.h`도 적어야 해요. 그러지 않으면 헤더를 고쳐도 다시 빌드되지 않아요. `make depend`가 이걸 대신 채워 줘요.

그런데 이번엔 헤더를 여기저기서 포함하다 보면 같은 정의가 여러 번 들어오지 않을까요?

## 10. 중복 정의와 ODR

**왜 생길까요?** [A p34] 프로그램은 헤더를 많이 포함하고, 헤더끼리도 서로 포함해요. 그래서 같은 정의가 여러 번 나타나기 쉬워요.

**타입만은 여러 .c 파일에 반복해도 돼요.** 이유를 차례로 보면 이래요.

1. 타입 정의(예: `struct`)는 모양만 설명해요. 메모리도, 링커가 볼 심볼도 만들지 않아요.
2. 각 `.c`는 따로 컴파일되니, 타입을 쓰는 파일마다 그 정의가 있어야 해요. 그래서 공유 헤더에 둬요.
3. 링커는 함수와 전역 변수만 연결하고 타입은 절대 연결하지 않아요. 그래서 여러 파일에 타입 정의가 있어도 충돌하지 않아요.
4. 단, 모든 파일의 타입 사본이 똑같아야 해요. 공유 헤더 하나를 쓰면 이게 보장돼요. C++의 ODR도 타입에 같은 규칙을 둬요.

| 중복 상황 | 허용? | 방지법 |
|---|---|---|
| 한 `.c` 안에서 같은 타입을 두 번 정의 | 안 됨(컴파일 오류) | include guard |
| 여러 `.c`에 같은 `typedef` | 됨 | 필요 없음 |
| 여러 `.c`에 같은 함수 정의 | 안 됨(링크 오류) | 한 번만 정의하고 헤더에 프로토타입 |

**ODR(One Definition Rule, 단일 정의 규칙)** [A p35]: 함수나 전역 변수는 프로그램 전체에서 한 번만 정의할 수 있어요. 두 번째 정의가 있으면 링크가 실패해요(multiple definition 오류). 선언(프로토타입, `extern`)은 모든 파일에 반복해도 돼요.

**예제** [A p35]: `document_editor.c`와 `spell_checker.c`가 둘 다 `struct Document`와 `printDocument()`를 정의했어요. `struct Document`가 두 파일에 있는 건 괜찮아요. 하지만 `printDocument()` 때문에 링크가 실패해요. 본문이 서로 달라도 마찬가지예요. 링커는 함수를 **이름만으로** 맞춰 보기 때문이에요. 이름을 바꾸거나, `static`으로 만들어 그 파일 안에 가두면 해결돼요(12절).

**고친 모습** [A p37]: `printDocument()`는 `document_editor.c` 한 곳에서만 정의하고, `document.h`에는 프로토타입 `void printDocument(Document doc);`만 둬요. 모든 `.c`는 `document.h`를 포함해요.

**링커 오류 읽기** [A p36]

```
spell_checker.c:(.text+0x0): multiple definition of `printDocument'; document_editor.o: first defined here
main.c:(.text+0x1e): undefined reference to `checkSpelling'
```

- `multiple definition`: 같은 함수나 전역이 `.c` 두 개에, 또는 두 파일이 함께 포함한 헤더에 정의돼 있어요. 정의를 하나만 남기고, 헤더에는 프로토타입이나 `extern` 선언만 남겨요.
- `undefined reference`: 이름은 선언했는데 정의가 없거나, 그 정의가 담긴 `.c`/`.o`를 빌드 명령에서 빠뜨렸어요. 정의를 추가하거나 gcc 명령이나 Makefile에 파일을 넣어요.

그런데 이번엔 **한 .c 파일 안에** 같은 헤더가 세 번 들어오는 문제(8절)는 어떻게 막을까요?

## 11. include guard와 #pragma once: "이미 읽은 대본" 표시

**정의** [A p37, p38]: include guard는 1절의 `#ifndef`를 이용해 헤더 내용을 한 번만 받아들이게 하는 장치예요.

```c
#ifndef DOCUMENT_H
#define DOCUMENT_H
typedef struct Document { char content[1024]; } Document;
#endif
```

**전처리 후 main.c에서 일어나는 일** [A p38]: `main.c`는 세 모듈 헤더를 포함하고, 각각이 `document.h`를 포함해요.

1. `document_editor.h`에서 온 첫 사본: `DOCUMENT_H`가 아직 없으니 `#ifndef`가 참이에요. `DOCUMENT_H`를 정의하고 `Document`를 정의해요.
2. `spell_checker.h`에서 온 두 번째 사본: 이제 `DOCUMENT_H`가 있으니 거짓이라 통째로 건너뛰어요.
3. `formatting.h`에서 온 세 번째 사본도 건너뛰어요.

가드가 없으면 `main.c` 안에서 `Document`가 세 번 정의되어 컴파일 오류가 나요. 가드는 첫 사본만 남겨요. 참고로 `typedef`만 반복하는 건 C11부터 괜찮지만, `struct` 본문을 반복하는 건 안 돼요.

**#pragma once** [A p39]: 헤더 맨 위에 `#pragma once` 한 줄만 쓰면 같은 효과를 내요.

- include guard는 표준 C라서 모든 컴파일러에서 동작해요. 하지만 헤더마다 고유한 매크로 이름이 필요해요. 두 헤더가 같은 이름을 쓰면 한쪽이 조용히 가려져요.
- `#pragma once`는 한 줄이고 이름이 충돌할 일도 없어요. C 표준은 아니지만 GCC, Clang, MSVC가 모두 지원해요.
- 이식성이 중요하면 include guard를 써요.

그런데 이번엔 함수가 아니라 **변수 하나**를 여러 파일이 같이 써야 하면 어떻게 할까요?

## 12. extern과 static: 공용 소품과 개인 소품

**왜 필요할까요?** [A p40] 민지 팀에는 페이지 크기와 언어를 담은 전역 설정이 있어요. 한 파일에서 정의하고 여러 파일에서 읽어야 해요. 반대로 편집기 안에서만 쓰는 카운터는 다른 파일이 건드리지 못하게 숨기고 싶어요.

**직관:** 무대 소품 가운데 공용 소품(`extern`으로 공유)과 배우 개인 소품(`static`으로 숨김)을 나누는 거예요.

**정의** [A p40, p41]

- `extern`은 "여기서는 선언만 하고, 정의는 어딘가에 있다"는 뜻이에요. 정의는 다른 파일에 있을 수도, 같은 파일에 있을 수도 있어요.
- **연결(linkage)** 은 링커가 그 이름을 파일 사이에서 이어 줄 수 있는지를 말해요.
  - 외부 연결(external): 모든 파일에서 보여요. 전역 변수와 함수의 기본값이에요.
  - 내부 연결(internal): 자기 파일에서만 보여요. 파일 범위에 `static`을 붙이면 돼요.
  - 연결 없음(none): 지역 변수와 매개변수예요.

```c
int sharedCount;            // 외부 연결
static int fileCount;       // 내부 연결
static void helper(void) { fileCount++; }   // 내부 연결
```

**static의 두 가지 뜻** [A p41]

- 파일 범위의 `static`: 다른 파일에서 이름을 숨겨요(가시성).
- 함수 안의 `static`: 호출이 끝나도 값을 유지해요(수명). 보이는 범위는 바뀌지 않아요.

```c
int nextId(void) {
    static int id = 0;   // 호출 사이에 유지
    int temp = 0;        // 호출마다 새로 0
    return ++id;         // 1, 2, 3, ...
}
```

**예제 1: extern으로 전역 공유** [A p42, p43]

```c
// config.h
extern Config globalConfig;            // 선언
// config.c
Config globalConfig = { .pageSize = 50, .language = ENGLISH };   // 정의는 한 번
```

1. `config.h`에 `Language` 열거형과 `Config` 구조체 타입, 그리고 `extern` 선언을 둬요. 타입은 메모리가 없으니 헤더에 두고(10절), 변수는 선언만 둬요(ODR).
2. `config.c`가 딱 한 번 정의해요. `config.c`도 `config.h`를 포함하므로 컴파일러가 선언과 정의가 일치하는지 검사해 줘요.
3. `main.c`는 `config.h`만 포함하고 `globalConfig.pageSize`를 읽고 `language`를 `FRENCH`로 바꿔요. 링커가 이 이름을 `config.c`의 정의에 이어 줘요.
4. `spell_checker.c`는 `globalConfig.language`를 읽어요. `document_editor.c`는 포함만 하고 쓰지 않아요.
5. `document_editor.c`의 `static int editorInstanceCount`와 `static void updateEditorInstanceCount()`는 그 파일 안에서만 보여요. 밖에서는 `initializeEditor()`, `printEditorInstanceCount()` 같은 외부 함수를 통해서만 써요.

**예제 2: extern과 static 연결 비교** [A p44–p47]

- `main.c`: `int documentsProcessed;`(외부 연결, 공유)와 `static int totalWordCount;`(내부 연결, main.c 전용)를 정의해요.
- `inputDoc.c`: `extern int documentsProcessed;`로 main.c의 변수를 가져와 1 늘리고, `int totalInputCharacters;`를 새로 정의해요. 이 변수는 main.c의 static `totalWordCount`와 다른 변수예요.
- `averageWords.c`: 둘 다 `extern`으로 가져와 `totalInputCharacters / documentsProcessed`를 계산해요.

`documentsProcessed`는 main.c에서 다른 두 파일로, `totalInputCharacters`는 inputDoc.c에서 averageWords.c로 흘러가요. `totalWordCount`는 static이라 main.c 밖으로 나가지 못해요. 다른 파일이 `extern int totalWordCount;`로 가져오려 하면 연결할 정의를 찾지 못해요.

> 보충: 그 경우 링커는 `undefined reference to 'totalWordCount'`를 내요(10절의 오류 유형).

## 한눈에 이어 보기

- 조건부 컴파일(`#if`/`#ifdef`/`#elif`) → assert와 `-DNDEBUG` → `#error`·`#warning`·`#pragma`
- `#pragma pack` → 정렬 규칙과 패딩(순서 바꾸면 32 → 24바이트) → `offsetof`·`_Static_assert`로 측정 → union(크기 = 최대 멤버, 타입 퍼닝, 레지스터 매핑)
- 미리 정의된 매크로(`__FILE__`, `__LINE__`, `__func__`) → assert의 실패 위치 출력
- 전처리 → 컴파일(파일별 `.o`) → 링크 → 선언은 `.h`, 정의는 `.c` 한 번 → 기능 플래그 `-D` → Makefile·타임스탬프 재빌드
- 중복 정의: 한 파일 안의 타입 중복은 include guard·`#pragma once`, 파일 간 함수 중복은 ODR(정의 하나 + 프로토타입) → `extern`으로 공유, `static`으로 숨김
